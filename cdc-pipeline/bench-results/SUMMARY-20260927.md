# Benchmark Summary — 2026-09-27

Paimon vs Iceberg CDC pipeline, ingest behaviour and StarRocks query performance.

**Run configuration**

| | |
|---|---|
| Flink parallelism | 64 (Paimon 1608 tasks, Iceberg 1032 tasks; 16 TMs each) |
| Source | RDS MySQL 8.0.45, `db.r6i.16xlarge`, io2 / 256,000 IOPS / 500 GB |
| Generator | `mysql-upsert-loadgen`, 10 pods × `RATE_PER_POD=50000`, `THREADS=8` |
| Engine | StarRocks `kube-starrocks-fe-0` + 3 BEs |
| Source data | `ecommerce` — customers, products, orders, order_items |

Raw artifacts: `starrocks-audit-20260927T115210Z.csv`,
`starrocks-audit-20260927T115558Z.csv`, `monitor-20260927b/` (20 JSON reports).

---

## 1. Headline result

Paimon is decisively faster on every query whose numbers can be trusted — up to
**48× on freshness** and **7.3× on a simple group-by**. The mechanism is visible
in the ingest metrics rather than inferred: Iceberg accumulates delete files that
every subsequent read must merge, and Paimon does not.

## 2. StarRocks query latency

From `starrocks-audit-20260927T115558Z.csv` (`Time` from the FE audit log, not
wall-clock — `kubectl exec` overhead is ~5.5 s and would swamp the measurement).

| Query | Paimon (ms) | Iceberg (ms) | Iceberg / Paimon | Trust |
|---|---:|---:|---:|---|
| Q1_count | 1,108 | 5,108 | **4.61×** | reliable |
| Q2_group_by | 740 | 5,403 | **7.30×** | reliable |
| Q3_join | 17,493 | 18,209 | 1.04× | reliable |
| Q5_time_window | 5,020 | 18,373 | **3.66×** | reliable |
| Q7_freshness | 203 | 9,810 | **48.33×** | reliable |
| Q4_product_sales | 22,365 | 7,981 | 0.36× | ⚠ suspect |
| Q6_multi_join | 43,443 | 8,137 | 0.19× | ⚠ suspect |
| Q8_hot_pk_lookup | 2,400 | 8,519 | 3.55× | ⚠ suspect |
| Q9_recent_window | 848 | 1,074 | 1.27× | ⚠ suspect |
| Q10_hot_join | 7,766 | 1,073 | 0.14× | ⚠ suspect |

**Paimon wins all 5 reliable queries.**

### Why 5 rows are marked suspect

Each suspect row reports **`scan_rows = 0` and `scan_bytes = 0` on one side**
while still reporting a multi-second `Time`. A query cannot scan zero rows and
zero bytes yet take 8 seconds. These readings are a measurement artifact — the
audit marker attributed a `Time` to a statement that short-circuited (cached
fragment or a plan that never reached the scan node), so the number does not
describe the same work on both engines.

The four apparent Iceberg wins (Q4, Q6, Q10, and Q9's near-tie) are **all** in
this group, and every one of them has `iceberg scan_rows = 0`. Iceberg did not
win those queries — it did not run them. Treat the reliable five as the result
and re-run the rest before drawing any conclusion.

Cross-run instability confirms the caution: Q3 moved 3,079 ms → 17,493 ms and Q6
27,909 ms → 43,443 ms between the two runs four minutes apart, because ingest was
concurrently rewriting both tables.

## 3. Ingest: the mechanism behind the query gap

Aggregated over 10 monitor reports per pipeline (`monitor-20260927b/`):

| | Paimon | Iceberg |
|---|---:|---:|
| Median throughput (rec/s) | 1,032,057 | 1,438,957 |
| New data files | 15,793 | 876 |
| **New delete files** | **0** | **1,443** |
| Position deletes | 0 | 135,286 |
| **Equality deletes** | **0** | **472,564,484** |
| Median checkpoint duration | 14,425 ms | 14,506 ms |

**Iceberg wrote 472.6 million equality deletes; Paimon wrote zero.** This is the
whole story. Iceberg's merge-on-read applies every one of those at query time.
Paimon's LSM compaction collapses updates in the background, so reads see merged
state — visible as *negative* `data_files_delta` in the reports
(`products -575`, `bytes_delta -302,184,329`: files being collapsed, not added).

Iceberg's higher median rec/s is not an advantage — it reflects processing fewer
total records (peak 488 M vs Paimon's 1.10 B) in burstier windows.

### Committer asymmetry

Measured earlier in the same deployment: `accumulated-backpressured-time` for
`order_items` was **110,772,534 ms (Iceberg)** vs **16,647,810 ms (Paimon)** —
6.7×. Sources sat at `busy=0.0` while `IcebergStreamWriter` burned ~1.6 M ms, and
**every `IcebergFilesCommitter` runs at parallelism 1** behind 64 parallel
writers. The bottleneck is Iceberg's commit path, and it appears during *ingest*,
before any query runs.

## 4. Table state and lag

From the `state` rows, `20260927T115558Z`:

| Table | Paimon rows | Iceberg rows | Iceberg files | Iceberg snapshots |
|---|---:|---:|---:|---:|
| customers | 80,562,660 | 80,568,811 | 2,342 | 14 |
| products | 163,257,194 | *(query failed)* | 477 | 15 |
| orders | 450,382,454 | 396,711,243 | 302 | 25 |
| order_items | 605,543,127 | 439,170,103 | 363 | 26 |

Iceberg trails by **53.7 M rows on `orders`** and **166.4 M on `order_items`**,
consistent with the `par=1` committer. `customers` shows Iceberg marginally
*ahead* (+6,151) — snapshot boundaries, not a real inversion.

Note `customers` holds **2,342 files for 80 M rows** while `orders` holds 302 for
397 M — small-file accumulation on the most-updated table, exactly what drives
Q7_freshness to 48× slower.

## 5. Load generator: contention, not capacity

The ~69 k rows/s plateau long attributed to an "RDS ceiling" is **workload
shape**, proven twice:

- **40 pods were slower than 8** — 2,000–7,500/s per pod vs 47,000/s.
  `Innodb_row_lock_current_waits 302` of `Threads_running 324`, average lock wait
  **5,499 ms**, max **62,159 ms**, 1,697,086 cumulative waits, 313 threads in
  `STATE=update` — while **IOPS were 79,658 of 256,000 (31%)**, CPU 24%, and
  `WriteLatency` 2.85 ms.
- At 10 pods the same signature persisted, milder: 80,044 IOPS (31%), CPU 18%,
  `DiskQueueDepth` 231, per-pod rates spread 233 → 29,460/s.

High queue depth with low latency and low CPU is contention, not disk.

### 2 M rec/s is unreachable on one instance

Measured per-row cost: **0.198 write IOPS/row** and **3.36 KB/row**. So 2 M
rows/s needs **395,818 IOPS** and **6,561 MB/s** — past io2's 256,000 IOPS
maximum and past `r6i.32xlarge`'s 5,000 MB/s. Even at io2's ceiling the binding
constraint becomes the instance's 2,500 MB/s EBS bandwidth → **~762,000 rows/s**,
using only 59% of provisioned IOPS. Reaching 2 M requires ~3–6 sharded
instances.

Confirming the model: gp3's arithmetic ceiling was ~323,381 rows/s and we
measured ~330,000, at which point `WriteIOPS` read 65,310 of 64,000 (102%).

## 6. Tuning attempt, and how the run ended

Applied to the 10-pod generator: `BATCH_ROWS` 2000 → 8000, `UPSERT_RATIO`
0.8 → 0.2, `HOT_KEY_RATIO` 0.95 → 0.5.

**No valid throughput measurement was obtained.** Mid-measurement the RDS
instance hit **`storage-full`** and shut down — every pod reported
`2003 (HY000) ... (111)`. `FreeStorageSpace` fell ~10 GB per 5 min and reached
0.77 GB at 12:45 UTC, below the 1.00 GB shutdown threshold.

The 0.2 upsert ratio did take effect before the outage (470,513 upserts vs
1,881,487 inserts = exactly 0.2), but 80% pure inserts consume space far faster
than in-place upserts, which is what exhausted the volume. The
`123,296 rows/s` reading taken during the rollout is **not comparable** to the
`164,231 rows/s` baseline: pods restart sequentially, so several were still in
their startup key-scan.

**Caveat on absolute file counts:** an earlier `iceberg-warehouse/` wipe was
declined, leaving ~67,240 orphaned objects. Iceberg's current-metadata pointer
lives in Glue table properties, so dropping the Glue tables did start the run
clean — but any storage-size or total-file-count comparison against that prefix
is distorted. The per-run *delta* metrics above are unaffected.

---

## Conclusions

1. **Paimon wins every trustworthy query**, 1.04× to 48.33×.
2. **The cause is measured, not assumed**: 472.6 M equality deletes vs zero.
3. **Iceberg's ingest bottleneck is its `par=1` committer**, costing 6.7× the
   backpressure and leaving it 166 M rows behind on `order_items`.
4. **Five of ten queries need re-running** — `scan_rows = 0` invalidates them,
   and all four apparent Iceberg wins are in that group.
5. **The generator is lock-bound, not IOPS-bound.** Past "RDS ceiling"
   conclusions should be re-read as workload shape.
